# MP3 下载性能优化实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 降低完整离线音频的下载耗时与客户端开销，保持现有播放、校验、暂停续传和已下载数据兼容。

**Architecture:** 先在客户端领域下载队列内实现有上限的文件并发，平台 I/O 继续通过 OfflinePort 隔离。合并进度通知和索引写入，并补齐中断恢复；服务端清单和按章打包由测量结果决定是否继续实施。

**Tech Stack:** npm workspaces、TypeScript strict、Expo 58、React Native、NestJS、Vitest、原生文档目录、Web CacheStorage。

## 全局约束

- Node.js 22.13+；包管理使用 npm。
- App、Server 分包维护，不互相导入源码；领域层不导入平台 API。
- 不变更音频来源、译文、录音及授权信息，不重新编码现有 MP3。
- 整章原始音频用于连续播放，独立经节文件用于原生单句循环。
- 整章及当前支持的经节文件全部完成 SHA-256 和大小校验，才能标记该章完整离线。
- 继续支持仅 Wi-Fi、手动暂停、原生当前文件续传、重启恢复、Android 后台通知与暂停操作。
- 保留旧索引和已有文件；删除离线音频不能删除阅读位置、词汇和收藏。
- 修改 Expo / React Native API 前读取 Expo 58 对应版本文档；新增原生依赖使用 expo install。
- 本文件最初仅记录计划；2026-10-25 用户已授权执行。实施在当前工作区进行，不自动部署或改动现有学习资料。

## 已知证据与判断边界

- 当前 downloadChapter 的文件循环逐个 await 下载，work 逐章等待完成。
- 离线包同时包含整章和经节音频；本地目录中创世记 1 每语言 32 个文件，英文总大小约为整章 2.72 倍，中文约 3.34 倍。
- 每个文件完成后等待 persist；现有元数据已按记录写入，但每次仍遍历快照并重写完整键索引。
- UI 和 Android 后台进度计算仍按单个 activePath / activeBytes 处理；后台每次更新会重新构建完整文件集合。
- 此前电脑到线上服务的一次整章请求约 1.33 MB / 0.15 秒，不能据此推断手机端带宽或长期服务端性能。
- 清单接口当前扫描全部录音引用并逐个查询文件；尚未测量其线上耗时，不能把它认定为已证实的主要瓶颈。

## 方案选择

| 方案 | 收益 | 代价 | 本次建议 |
| --- | --- | --- | --- |
| 有限并发 + 减少进度和存储开销 | 减少小文件等待，复用现有接口及文件 | 需要处理多任务暂停、进度及恢复 | 优先实施 |
| 按章打包，客户端下载后恢复独立文件 | 显著减少请求数，适合整卷下载 | 增加包生成、临时空间、解包和跨端适配 | 第一轮优化后按测量决策 |
| 只下载整章，分节按需下载 | 减少首次下载流量 | 改变完整离线单句循环的可用性和状态定义 | 不作为当前默认方案 |

- [x] 先写失败回归：人为挂起前四个下载，断言同时启动四个、第五个等待；完成一个后第五个补位，任何时刻不超过上限。
- [x] 保持逐章排队；每章内部使用共享文件队列和最多 4 个 worker，整章文件先进入队列。并发数通过构造参数供测试/调优，默认 4，不新增用户设置。

- [x] 暂停或仅 Wi-Fi 条件失效时，先停止派发、取消该章所有活动任务，等待全部落定，再完成暂停与持久化。

- [x] 手动暂停后网络变化不得自动重启；删除等待活动任务完全退出，防止文件删完又被下载任务写回。

**验收：** 严格遵守并发上限；进度不重复计数、不超过 100%；所有必需文件校验后才 complete；原有回归继续通过。

- [x] 先写回归：高频进度事件下，界面通知频率有上限；暂停、失败、完成等状态立即可见。
- [x] 字节进度至多每 200 ms 通知一次；完成、暂停和错误立即通知并清理待发计时器。
- [x] 在下载集合改变时重建去重文件表和总大小，进度事件只更新活动文件字节；前台与通知使用同一汇总规则，避免各自反复遍历全部文件。
- [x] 使用脏记录集合处理本轮变更，避免每完成一个文件遍历全部已下载记录；继续序列化原子写入。
- [x] 持久化触发条件为距首次未保存变更达到 500 ms 或累计 8 个完成文件，任一先到即触发；暂停、章完成、失败、删除、进入后台时强制刷盘。

- [x] 模拟杀进程发生在文件完成与索引刷盘之间，验证重新打开并恢复任务后复用已完成文件；损坏文件必须重新下载。
- [x] 写失败保留脏记录并暴露 storage 错误，不能因定时批量写入而吞掉持久化失败。

## 第二轮候选：按章打包传输

第一轮完成后，若小文件请求等待仍占主要耗时，再实施独立计划：

1. 按章节、语言和资源集合版本生成不可变包；整章及逐节文件打包，不重新编码，MP3 已压缩，重点收益是减少请求数。
2. 包在后台预生成并原子发布，不能让一次下载请求触发同步切割、转码或重建。
3. 提供包大小、包 SHA-256 和逐文件清单；原生支持包文件 Range 续传，Web 明确恢复策略。
4. 解包前预留包与解包结果的峰值空间；限制成员路径、数量、解包大小，逐文件校验后原子转入现有资产目录。
5. 下载失败或客户端不支持包时回退逐文件下载；优先复用已有文件，避免仅缺少一节时重新拉整包。
6. 保留独立 MP3 与现有播放方式；打包不会减少音频本身占用，不能承诺 2～3 倍流量缩减。

**执行顺序：** 基线 → 客户端有限并发 → 进度与持久化优化 → 有条件清单优化 → 完整验证；按章打包作为测量后的第二轮决策。


## 2026-10-25 执行记录

- 客户端：已实施章内并发 4、按路径汇总进度、200 ms 进度合并、500 ms / 8 文件合并检查点、进入后台刷盘。
- 恢复：原生与 Web 均增加独立的 SHA-256 / 大小恢复检查；完整文件在空间预检之前恢复，避免空间不足时重复下载或误报。
- 竞态修正：准备、入队、暂停、恢复和删除统一串行操作；worker 取消后全部落定再继续；章节使用一致的空间准入预算，避免重复扣算正在增长的临时文件。
- 服务端：媒体元数据按最多 8 个并发检查，保留现有接口、顺序和目录更新行为。
- 回归：并发上限、暂停/仅 Wi-Fi、存储写失败、恢复、删除竞态、空间预留、并发进度与检查点均有自动化覆盖；关键缺陷先观察失败测试后修正。
- 性能：新增默认跳过的真实 HTTP 基准，可比较并发 1 / 4；使用固定清单快照、每种配置三次、临时 Node 文件存储。结果及复现命令见 `docs/audio-download-performance.md`。
- 自动验证与构建结果以性能记录为准。
- 未连接 Android 真机，手机耗时、锁屏/系统强停/通知交互及真实浏览器存储验收仍待设备验证；不把 Node 结果当作手机性能结论。
- 按章打包仍为第二轮候选，本轮没有改变离线包内容或播放行为。
